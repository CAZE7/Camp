# Safety Case — Camp (Elektrikplaner)

**Stand:** 2026-11-04  
**Status:** Verbindlich (Erstfassung, lebendes Dokument)  
**Verantwortlich:** Safety Engineering (Argumentation), QE (Nachweise), Product Owner (Freigabe)  
**Übergeordnet:** `docs/safety/SAFETY-PLAN.md`, `docs/safety/RISK-REGISTER.md`, `docs/engineering/ENGINEERING-CONSTITUTION.md`  
**Zweck:** Nachweis, dass zentrale Sicherheitsbehauptungen von Camp durch Argumentation und Belege gestützt sind. Ein grüner CI-Lauf ist **kein** vollständiger Sicherheitsnachweis.

---

## 1. Struktur des Safety Case

Der Safety Case folgt der Kette:

**Sicherheitsbehauptung → Argumentation → Nachweis → Bewertung → Restrisiko**

Jede zentrale Sicherheitsbehauptung (Claim) dokumentiert:

| Element                    | Bedeutung                                                                                                                                |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **Claim-ID**               | Eindeutige ID (CL-001 …)                                                                                                                 |
| **Behauptung**             | Was wird behauptet (z. B. „Sicherung schützt Kabel nie oberhalb der Kabelgrenze“)                                                        |
| **Argumentation**          | Warum die Behauptung im System gilt (Architektur, Regel, Konstruktion)                                                                   |
| **Nachweis-Kategorie**     | Mathematisch nachgewiesen / durch Tests verifiziert / anhand externer Datenquellen belegt / fachlich unabhängig geprüft / noch ungeklärt |
| **Nachweis-Referenz**      | Testdatei, Architekturtest, ADR, Review-Protokoll, Datenblatt-Quelle                                                                     |
| **Ergebnis**               | Erfüllt / Offen / Teilweise                                                                                                              |
| **Restrisiko**             | Verweis auf Risk Register (R-XXX)                                                                                                        |
| **Verantwortlich / Datum** | Wer hat den Nachweis geprüft, wann                                                                                                       |

---

## 2. Einstufung von Nachweisen (verbindlich)

Jeder Nachweis im Safety Case muss einer der folgenden Kategorien zugeordnet sein. Mischformen sind explizit als solche zu kennzeichnen.

| Kategorie                               | Bedeutung                                                                                                                             | Anforderungen                                                                               |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **mathematisch nachgewiesen**           | Eigenschaft gilt für alle möglichen Eingaben (z. B. durch fast-check Property, typisierte Invarianten, deterministischer Algorithmus) | Property-Test über generierte Fälle, deterministischer Nachweis (Doppellauf byte-identisch) |
| **durch Tests verifiziert**             | Eigenschaft geprüft über definierte Testfälle (Unit, Integration, E2E, Regression)                                                    | Testdatei, Abdeckung, Negativfall                                                           |
| **durch E2E verifiziert**               | Eigenschaft auf Systemebene gegen gebauten Static Export geprüft                                                                      | Playwright-Spec, Projekt 375/768/1440                                                       |
| **anhand externer Datenquellen belegt** | Wert stammt aus Datenblatt, Norm, Herstellerangabe mit Quellenreferenz                                                                | Quellenangabe, Datum, Hersteller, Modell, Datenblatt                                        |
| **fachlich unabhängig geprüft**         | Zweite Person (nicht am Code beteiligt) hat die Behauptung geprüft                                                                    | Review-Protokoll, PR-Genehmigung                                                            |
| **noch ungeklärt**                      | Behauptung ist nicht oder nicht hinreichend belegt; offenes Restrisiko                                                                | Risk-Register-Eintrag, Zieltermin, Verantwortlicher                                         |

**Regel:** Eine Behauptung ohne Kategorie und ohne Referenz gilt als „noch ungeklärt“ und blockiert den Release, wenn sie sicherheitsrelevant ist.

---

## 3. Warum ein grüner CI-Lauf kein Sicherheitsnachweis ist

Ein grüner CI-Lauf beweist nur, dass die automatisierten Checks zum Zeitpunkt des Laufs grün waren. Er beweist **nicht**:

- dass fehlende technische Daten nicht still als Grenzwerte eingesetzt werden (Regel M / S-3),
- dass die 230-V-Modellgrenze korrekt ausgewiesen ist (R-005, `NET-003`),
- dass ungeprüfte Herstellerangaben nicht als verifizierte Fakten dargestellt werden (Datenqualität),
- dass die elektrische Berechnung für alle Randfälle korrekt ist (Tests decken nur getestete Fälle ab),
- dass ein Review stattgefunden hat (menschliche Kompetenz),
- dass die Dokumentation mit dem Code übereinstimmt.

Der Safety Case dokumentiert deshalb explizit, welche Behauptungen **nur** durch CI abgedeckt sind und welche zusätzliche Nachweise benötigen.

## 5. Bewertungsregeln für den Safety Case

| Regel | Bedeutung                                                                                                                                           |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| B-1   | Eine Behauptung der Klasse S (sicherheitskritisch) benötigt mindestens eine Kategorie außer „noch ungeklärt“, bevor sie als erfüllt gilt.           |
| B-2   | „Noch ungeklärt“ ist ein zulässiger Zustand, muss aber im Risk Register als offenes Restrisiko mit Verantwortlichem und Zieltermin stehen.          |
| B-3   | Widerspruch zwischen Claim und Code/Tests: Der Safety Case ist nicht konsistent; der Merge ist blockiert bis zur Auflösung.                         |
| B-4   | Jede Änderung an sicherheitskritischen Dateien (SC-1, Constitution §5) erfordert eine Aktualisierung der betroffenen Claims.                        |
| B-5   | Der Release wird nur freigegeben, wenn alle Claims der Klasse S entweder „Erfüllt“ oder dokumentierte Restrisiken mit Product-Owner-Akzeptanz sind. |

## 7. Freigabeentscheidung

Die finale Release-Freigabe erfolgt durch den Product Owner auf Basis dieses Safety Case, des Risk Registers und der Requirements Matrix. Die Entscheidung dokumentiert:

- welche Claims erfüllt sind,
- welche Restrisiken akzeptiert werden und warum,
- dass kein sicherheitskritischer Fehler durch niedrige Priorisierung oder einen grünen Testlauf als erledigt gilt.
